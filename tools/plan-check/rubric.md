# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis is grounded | The plan's stated cause, read against every step of the repro-evidence block: the artifact it shows, and the result of each control run. | Pass if the stated cause is consistent with everything the repro evidence shows, including every control (a control that succeeds without the mechanism the plan blames does not contradict a cause that only requires that mechanism when present). Fail if any step or control in the repro evidence rules the stated cause out (the same input still fails with the blamed mechanism absent, or the same input still succeeds with it present), even if the plan writes the cause with total confidence. `unclear` if the repro evidence does not pin down the behavior well enough to check the cause against it. | required |
| Scope is bounded | The plan's stated in-scope/not-in-scope boundary, read against everything the approach or files/areas section actually describes doing. | Pass if the described change addresses exactly what the issue and repro evidence call for, with an explicit not-in-scope line naming what the plan deliberately leaves out. Fail if the approach includes a rewrite, migration, new abstraction layer, redesign, or "while I'm in there" work beyond what the issue's own evidence requires — even when the core fix inside that plan is correctly diagnosed and would itself be fine alone. A plan that defers extra work explicitly ("not in scope: X, because Y") passes on that deferral; a plan that just does the extra work fails regardless of how good the central fix is. | required |
| Executable by a stranger | The plan's approach and files/areas section. | Pass if the plan names concrete files or areas and a single chosen approach, in enough detail that someone who has never seen the issue could start working without asking the author anything. Fail if any decision that matters to starting the work is left open at plan time — an unnamed file, an unchosen approach among options, "investigate X to find the fix," "upstream or vendored, whichever is easier." Exploration steps are fine only when they sit inside an already-bounded, already-chosen fix (e.g. "grep for the same pattern at nearby call sites"), not when the fix itself is what's still being discovered. | required |
| Test plan is decisive | The plan's test plan, read against the repro-evidence block's steps and artifact. | Pass if the test plan names a specific, observable outcome tied to the actual fix: re-running the repro evidence's own steps (or a named regression test) and stating what result confirms the fix (an exit code, an absence of a specific error, a specific value). Fail if the test plan names no fix-specific observable outcome — "run the full test suite," "shouldn't feel broken," "should be faster" — even when the rest of the plan is strong. Running the full suite in addition to a named, fix-specific check is fine; running it as the *only* stated check is not. | required |
| Honesty about unknowns | The plan's stated risks, unknowns, and any deviation notes, read against how the rest of the plan states its claims. | Pass if the plan either has no claims that need hedging, or explicitly labels its genuine unknowns and open questions as such rather than asserting them as settled. Fail if the plan states an unverified claim (an untested performance assumption, an unconfirmed root cause beyond what the repro evidence supports, a guess about another platform never tested) as flat fact, with no hedge, where the rest of the package shows it was never actually checked. `unclear` counts as fail: an unresolved unknown the plan never surfaces is exactly the failure this check exists to catch. | required |
| Comms fit the room | The plan comment's text, read against the thread-highlights block for explicit maintainer direction, and against the repo-facts block's stated AI-use disclosure requirement. | Pass only if both hold: (a) when the thread contains an explicit maintainer-identified cause, fix location, or request (e.g. a maintainer names the exact file/line at fault, or asks the reporter to test a specific patch), the plan comment's approach engages that direction rather than pursuing an unrelated path in silence; and (b) when the repo's stated contribution policy requires disclosing AI assistance, the comment discloses it. If the thread has no maintainer direction to engage, (a) passes automatically; if the repo states no AI-disclosure requirement (silent, or permissive-with-responsibility), (b) passes automatically. Fail if either applicable condition is violated. | required |

## Verdict rule

Accept only if every required check passes. Any required check graded `fail` holds the package (`reject`). Treat `unclear` the same as `fail`: a plan whose grounding, scope, buildability, test plan, honesty, or comms this rubric cannot verify is not ready to post and build from. There are no `preferred` checks in this rubric — every family the checks table names is load-bearing, because the eval set's five categories (clear-accept, scope-creep, wrong-cause, unbuildable, thread-convention) each turn on one of these checks failing.
