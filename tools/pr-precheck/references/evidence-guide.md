# Evidence guide: where evidence lives in a PR package

## Plan fidelity (harness category: silent-drift)

Where it lives: in an eval bundle, the plan-context block's scope statement (named files/areas, its not-in-scope line, any deviation note) and the candidate PR's diff (every changed file and hunk) and description (its claims about what it changed). In live mode: `plan.md` (including any deviation section filled after a build), the output of `git diff main...HEAD` on the student's branch, and `pr_draft.md`'s description.

What good looks like: every changed file or hunk is inside the plan's stated boundary, or is explicitly covered by a deviation note that both the plan and (when it changes the posted intent) the description restate — pkg-13's `%VAR%` deferral and neovim#41337's description that "restates it so reviewers can weigh the limit" is the model. What silent drift looks like, in both directions: *more* than the plan (pkg-03's unrequested `truncate()` rewrite and new `resolve_symlinks` option riding alongside the one-line fallback fix, pkg-06's renaming pass and new settings flag, pkg-09's unannounced new `--time-format` flag, calib-03's silent rewrite of `print/property.js`, a file the plan never touches) and *less* than the plan with a claim of completeness (pkg-17's description claiming the docs "now document the limitation" when the diff contains no docs change at all). The description's own fidelity language is graded here, not as a comms nicety: "implements the plan exactly" or "no other changes" is a factual claim about the diff, and it is drift the moment the diff disagrees with it — in either direction.

## Test evidence (harness category: not-tested)

Where it lives: in an eval bundle, the plan-context block's test plan (every scenario it names) and repro evidence, read against the candidate PR's test-evidence section. In live mode: the plan's test plan in `plan.md`, the student's week-2 repro steps (or the house repro pack), read against `test_evidence.md`.

What good looks like: a concrete, shown before/after for the plan's *primary* scenario — the actual issue repro, actually re-run, not narrated — and at least a specific, concrete claim (not necessarily a full transcript) for every *other* scenario the plan's test plan named. pkg-05, pkg-08, pkg-13, and pkg-16 all pass this way: the main repro gets a real before/after transcript, and a secondary scenario (a same-key warning, a control case, an unchanged control) gets either its own transcript or a specific stated claim tied to a named regression test — nushell's `same_name_same_key_replaces_with_warning` test and the stated "`cargo test -p nu-protocol` passes (312 tests)" together cover the warning scenario pkg-05's test plan named, without a separate manual transcript for it. What fails this family is different in kind, not degree: calib-04's rejection turns on a scenario the plan's test plan named (the `--exec` abort) going entirely unaddressed anywhere in the PR — no claim, no test, no mention, not even a narrated one. The evidence must also exercise the actual trigger the fix touches, not an adjacent path that happens to pass: pkg-07's single-file control never exercises the two-file path the bug and the fix are about, and pkg-14's casing test exercises the unchanged GET path instead of the POST Content-Type repro the issue and plan are about. And the primary scenario itself must be shown, not asserted: "tested locally, colors work now," "verified working on my machine for a full day" (pkg-04, pkg-10) have no transcript behind them at all, which is a harder failure than a secondary scenario's test coverage being less than a full transcript. The repo's own suite needs a named command and a stated outcome — "`cargo test -p nu-protocol` passes (312 tests)" is ideal, but "`go test ./pkg/minikube/machine/... ./cmd/...` passes" (pkg-16, no count given) is still enough because it names the actual target; what fails is a bare "tests pass" floating with nothing else in the PR to anchor it.

## Diff quality (harness category: unreviewable)

Where it lives: in an eval bundle, the candidate PR's unified diff and commit list. In live mode: the branch's diff and `git log` on the branch.

What good looks like: the diff reads as exactly the fix, nothing more. The debris tells, concretely, from the eval set: a commented-out prior attempt and a commented-out debug `eprintln!` sitting next to the real fix (pkg-12), a dead function kept behind `allow(dead_code)` "for reference" (pkg-12, pkg-15), a bare `// TODO` dropped on an unrelated import, pure re-indentation or import-restructuring churn with no functional content (pkg-15, pkg-18), duplicate blocks of identical re-printed lines (pkg-18), and commit messages that describe nothing ("wip," "fix," "fmt + cleanup," "misc cleanups while debugging" — pkg-12, pkg-15). A single clean commit with a real message, or a short diff with no such debris, passes even when terse (pkg-19, pkg-11): brevity is not the failure mode here, leftovers are.

## Standards and comms (harness category: standards-wall)

Where it lives: in an eval bundle, the repo-facts block's stated PR-template sections/checklist and its stated contribution/AI-disclosure policy, read against the candidate PR's description and diff; the thread-highlights block for explicit maintainer-authored direction, read against the PR's approach. In live mode: the repo's actual `.github/PULL_REQUEST_TEMPLATE.md` and `CONTRIBUTING.md`/AI-policy files per `scope.md`, read against `pr_draft.md`, and the live issue thread.

What good looks like: every section or checklist item the template requires has real, specific content — and when the template requires an accompanying file (a changelog entry, a `whatsnew` entry, docs), that file must actually be present in the diff, not just promised in prose. pkg-01 is the clean failure: decisive ASAN evidence and a good description, held back purely because pandas' required checklist items (closes-#, tests-added checkbox, the `whatsnew` entry) are visibly missing from both the description and the diff. AI disclosure is the other half: when the repo's stated policy requires it (ghostty's AI_POLICY.md), the description must actually disclose tool and extent of use — pkg-20 fails this alone, on an otherwise excellent, maintainer-directed fix; pkg-11 shows the pass case, an "own-words AI disclosure per the repo's stated policy." Maintainer direction is the third strand: when a maintainer already authored the diagnosis or asked for a specific approach (pkg-20's issue is maintainer-authored and the plan explicitly "adopts the issue author's diagnosis... a maintainer wrote the issue, so the direction is settled"), the PR must follow it, not silently diverge. When the repo states no template requirement, no AI-disclosure duty, or the thread holds no maintainer direction, that part of the check has nothing to violate and passes automatically. (Whether the description's *fidelity* claims match the diff is plan fidelity, above — this family is about the repo's *standards* asks, not about drift.)
