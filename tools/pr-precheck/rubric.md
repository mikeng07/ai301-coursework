# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Plan fidelity | The diff's changed files and hunks, read against the plan's stated scope (its named files/areas and its not-in-scope line) and any deviation note in the plan; separately, the PR description's claims about what changed (fidelity claims, e.g. "exactly as planned," "no other changes"), read against what the diff actually contains. | Pass if every changed file or hunk falls inside the plan's stated scope, or is covered by an explicit deviation note (in `plan.md` or restated in the description) explaining what changed and why, AND the description's fidelity claims match the diff exactly — it claims neither more than the diff delivers nor less. Fail if the diff touches a file, adds a flag/option, or changes behavior the plan did not scope in and no deviation note covers it (an "adjacent" or "while I'm in there" addition counts, however small), or if the description asserts something the diff contradicts in either direction (claiming full fidelity over an untouched file the diff silently changes; claiming a capability — e.g. "docs updated" — that the diff does not contain). An honestly stated, explicitly scoped-out deferral that both the plan and the description name is not drift and passes. | required |
| Test evidence | The PR's test-evidence section, read against every scenario the plan's own test plan names (not just one of several) and against the repro evidence's steps; separately, whether the repo's own checks/test suite were run and their outcome shown. | Pass if (a) the plan's primary/triggering scenario (the actual issue repro) has a concrete, shown before state and after state produced by actually re-running the named repro steps — not a paraphrase of what should happen; (b) every other scenario the plan's test plan named (a control, a secondary case, a warning) is at minimum addressed with a specific, concrete claim about what was observed (a stated result, a named regression test whose assertion covers it) rather than left unaddressed — a full manual transcript for every secondary scenario is not required, but silence on a named scenario is not addressing it; and (c) the repo's own checks/suite are stated as run, naming the actual command or test target, with a stated pass outcome (a pass count is good when given but not required; a content-free "tests pass"/"cargo test passes" with no named command and no other evidence anywhere in the PR is not enough on its own). Fail if the primary scenario has no shown artifact at all ("tested locally, works now," "verified for a full day"), if the shown evidence exercises a code path other than the one the fix actually touches (a control or an unrelated input standing in for the real trigger), or if a scenario the plan's test plan named is entirely unaddressed anywhere in the PR (no claim, no test, no mention). | required |
| Diff quality | The unified diff and the commit list. | Pass if the diff contains only the fix plus directly-related test, doc, or changelog additions the plan calls for, with commit messages that describe what changed. Fail if the diff carries any debris: commented-out code (a prior attempt, a disabled line), dead code (an unused function, especially behind a lint-suppression attribute), debug prints or eprintln/console.log left in, a bare TODO on unrelated code, pure formatting/re-indentation churn unconnected to the fix, or an unrelated hunk riding along; also fail if a commit message is a content-free placeholder ("wip," "fix," "fmt + cleanup") that hides what it changed. One data point is not a trend: a single well-named commit or a clean single-purpose diff passes even if terse. | required |
| Standards and comms | The repo-facts block's stated PR-template sections/checklist and its stated contribution/AI-disclosure policy, read against the PR's actual description and diff; separately, any explicit maintainer-authored direction in the thread or issue, read against what the PR does. | Pass only if every section or checklist item the repo's stated template requires is present with real, specific content (not a boilerplate restatement) — including any accompanying file change the template names as required (e.g. a changelog/whatsnew/docs entry), which must actually appear in the diff, not just be described in prose; AND, when the repo's stated policy requires disclosing AI assistance, the description discloses it; AND, when the thread contains an explicit maintainer-authored diagnosis or direction, the PR's approach follows it rather than silently diverging. When the repo states no template requirement, no AI-disclosure requirement, or the thread holds no maintainer direction, that half of the check passes automatically for lack of anything to violate. Fail if a required template section/file is missing or empty, if a stated AI-disclosure requirement is unmet, or if the PR silently ignores explicit maintainer direction present in the thread. | required |

## Verdict rule

Accept only if all four required checks pass. Any required check graded `fail` holds the package (`reject`). Treat `unclear` the same as `fail`: a PR whose fidelity, evidence, cleanliness, or standards-compliance this rubric cannot verify from the package is not ready to submit. There are no `preferred` checks — the eval set's four failure categories (silent-drift, not-tested, unreviewable, standards-wall) map one to one onto these four checks, and a package that fails none of them is a clear-accept.
