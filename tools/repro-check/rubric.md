# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded | The repro report's environment line (tool/runtime version, OS, install method), read against the repo-facts block's latest-release line and, where the issue's behavior is build-profile-sensitive (debug vs. release), against which profile was used. | Pass if the report states the tool version, the OS, and how it was built/installed. If the issue's behavior is known to differ by build profile, pass only if the report also names the profile used. Missing any of these fails the check. | required |
| Steps runnable by a stranger | The repro report's steps/commands, read for whether every input, file, or command needed is fully given in the report itself. | Pass if someone outside the repo, with only the report in hand, could execute the same steps from a cold start. Fail if the steps rest on a private repo, an unshared config, or any resource the report does not include. | required |
| Faithful trigger | The input, command, and arguments used in the repro report, compared against the issue's stated trigger (its command line, its input file's contents, its argument values) to decide whether they exercise the same triggering condition. | Pass if the trigger exercises the same condition the issue describes — the same operator/mechanism and the same kind of input — even if minimized or self-authored (a smaller file that still contains the same invalid section, a shorter command that still hits the same code path). A deliberate variation from the issue's exact version/environment (e.g. a control run, a version bump) also passes if the report labels it as a variation. Fail if a different operator, argument, or input class produced the artifact (changing what the input actually means, not just its size) and the report presents it as confirming the issue anyway. | required |
| Outcome is honest and evidenced | The artifact (output/log/error text) the report shows, read against the issue's described behavior, and the report's stated conclusion (Expected vs. Actual, or a claim of confirmation/cannot-reproduce) read against what that artifact actually demonstrates. | Pass if either: (a) the shown artifact, produced by the faithful trigger, is the same class of failure the issue describes (same error signature, same crash, same missing behavior), or (b) the report attempted the faithful trigger, did not get the issue's behavior, and says so plainly, naming what differed (an honest cannot-reproduce). Fail if the report shows no real artifact at all (a bare assertion like "confirmed" or "definitely reproducible" with no quoted output), if the shown artifact is a different failure than the issue reports but is narrated as confirmation, or if the conclusion claims more than the artifact shows (e.g. testing an unacknowledged different version and treating the result as evidence about the current one). | required |
| Claim comment is specific, not boilerplate | The candidate claim comment's text. | Pass if the comment names something concrete about this issue: the actual symptom, the area of code, or a specific plan. Fail if the comment is interchangeable template language, pure emotional agreement ("+1," "this drives me nuts"), or an unconditional promise ("guaranteed fix," a fixed timeline) with nothing behind it. | required |
| AI-use disclosed where required | The repo-facts contribution-policy line for a stated AI-disclosure requirement, and the claim comment plus repro report text. | Pass automatically if the repo states no AI-disclosure requirement (silent or permissive-with-responsibility policies both pass here). If the repo's stated policy requires disclosing AI assistance, pass only if the comments disclose it. | required |

## Verdict rule

Accept only if every required check passes. Any required check graded `fail` holds the package (`reject`). Treat `unclear` the same as `fail`: proof this rubric cannot verify is not proof the package is ready to post. There are no `preferred` checks in this rubric — every family the checks table names is load-bearing, because the eval set's five categories (clear-accept, no-evidence, wrong-target, unfollowable-comms, disclosure) each turn on one of these checks failing.
