# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Maintainer alive | The repo-facts block's last 5 default-branch commit dates and maintainer first-response sample (or the archived flag). | Pass if the repo is not archived, and either a default-branch commit landed within the last 90 days (of the capture date in eval mode, of today in live mode), or a commenter with an Owner/Member/Collaborator badge replied to a recent issue within the last 30 days. Fail if archived, or if neither signal is present. | required |
| Repo is in active use | The repo-facts block's latest-release date, last-push-to-any-branch date, and adoption signal (stars / "used by" counter). | Pass if a release or a push to any branch happened within the last 12 months, or, for a project without a formal release cadence, the adoption signal (a meaningful star count, or a stated "used by" count) shows the software is actually run by people. Fail if the last push/release is over a year old and no adoption signal is given. | required |
| Scope fits a newcomer | The issue's body and comment thread. | Pass if the issue names one concrete target problem or feature with no essential decision left open — no "TBD," no "perhaps we could," nothing waiting on a product call nobody has made. Within that, any of these are still bounded, not scope creep: touching several files that all serve the one named target (a docs page plus the pages that reference it); an issue's own author (maintainer or reporter) naming several viable approaches, causes, or sub-fixes to their own single described problem (a diagnosis plus a menu of possible fixes is still one target: the named problem going away), letting whoever picks it up implement any one of them rather than all of them; an explicitly-marked optional/lower-priority extra that the issue itself says is not required; or a trailing "etc." after a few named examples of the *same kind* of instance (e.g. several rules needing the same kind of preview) — that names one recurring, mechanically-discoverable task, not a list of separate deliverables. Fail if: the issue enumerates multiple *separate*, independently-shippable items presented as a list to be split into their own issues/PRs (a tracker, not facets of one feature); the core target itself is undecided and no maintainer has ever confirmed it (including an issue that has sat for years accumulating repeatedly abandoned claims with no maintainer ever locking the spec — that pattern is itself evidence the spec was never settled); a maintainer states the fix touches core internals; or the issue is a support question rather than a change. | required |
| Nobody is already on it | The issue's Assignees field, its linked-PR state (Development box and PRs mentioned in the thread), and claim comments in the thread with their dates. | Pass if there is no assignee, no open linked PR, and no claim comment that shows current follow-through. A claim blocks the issue only while it shows follow-through: an open linked PR, or activity (the claim itself, a maintainer reply to it, or related commits) within the last 90 days (of the capture date in eval mode, of today in live mode). A claim with no linked PR and no activity in that window is stale and does not block a newcomer, even if a stale-bot once nudged it or a maintainer once said "go ahead" long ago. An open linked PR blocks regardless of its age (hours-old counts). Fail if any current signal shows someone already working on it. | required |
| AI-assisted contribution is allowed | The repo-facts block's contribution-policy line: `CONTRIBUTING.md`, any dedicated AI-policy file, and PR/issue templates. | Pass if the repo states no ban on AI-generated contributions — silence, or conditions like disclosure/personal-understanding/testing requirements, all pass here. Fail only if the repo's stated policy bans AI-generated code or documentation outright. | required |

## Verdict rule

Accept only if every required check passes. Any required check graded `fail` rejects the issue; treat `unclear` the same as `fail` — a signal I could not find is not a signal that clears the issue. There are no `preferred` checks: the fit profile in `scope.md` handles ranking among accepted issues, so no rubric check is needed just to rank rather than gate.
